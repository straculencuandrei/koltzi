Core Triage Metric

Shannon Entropy

Measuring data unpredictability to spot packing and encryption

Shannon entropy measures the uncertainty or randomness of byte values in a dataset, ranging from 0.00 (all bytes identical) to 8.00 (maximum possible uniform randomness).

0.00 - 4.50
Plaintext strings, zero-padding, sparse lookup tables
4.50 - 6.80
Standard compiled x86/x64 instructions and resource data
6.80 - 7.20
Dense algorithms, multimedia assets, mild obfuscation
7.20 - 8.00
Encrypted payloads, shellcode stagers, packed executables (UPX)
Why it matters in Koltzi

Malware authors compress or encrypt their malicious payload to evade static antivirus signatures. An executable section with entropy above 7.20 or an overlay above 7.80 almost certainly unpacks itself in memory at runtime before transferring execution to its payload.

Memory Layout

PE Sections (.text, .rdata, .data)

Virtual memory segments loaded by Windows into execution space

A Portable Executable (PE) divides its content into distinct sections, each mapped with designated page permissions:

  • .text / CODE: Contains native CPU instructions. Typically marked Execute and Read (RX).
  • .rdata: Read-only data including string literals, constant values, and the Import Address Table (IAT).
  • .data: Global and static variables writable by the application at runtime (RW).
  • .pdata: Structured exception handling unwind tables required for x64 stack unwinding.
  • .rsrc: Application icons, manifests, dialog templates, and localized assets.
Triage Takeaway

Legitimate binaries follow standard section naming conventions. Non-standard section names (like .upx0, .themida, or randomized strings) or tiny raw sizes compared to large virtual sizes indicate code unpackers.

Security Violation

W^X Memory Policy (Write XOR Execute)

Preventing code segments from modifying themselves at runtime

The Write XOR Execute (W^X) principle mandates that memory pages can either be Writable OR Executable, never simultaneously. Modern operating systems enforce this through Data Execution Prevention (DEP).

When a section or memory allocation is marked PAGE_EXECUTE_READWRITE (RWX), code can dynamically overwrite its own instructions without re-protecting pages via VirtualProtect.

Triage Takeaway

Normal software almost never contains RWX sections. The presence of RWX sections or API calls requesting RWX protections is a primary indicator of shellcode decoders, in-memory stagers, and process injection techniques.

Loader Architecture

Import Address Table (IAT)

Dynamic function pointer resolution from shared system libraries

When a program calls external Windows APIs (such as MessageBoxW or CreateFileW), it does not contain the function implementation. Instead, the PE header includes an Import Directory listing required DLLs and function names.

At load time, the Windows PE loader resolves these symbols, loads the DLLs into the process virtual address space, and writes the actual memory addresses of each function into the IAT.

Triage Takeaway

Examining imported functions reveals binary capabilities. If a binary only imports LoadLibraryA and GetProcAddress, it resolves its real capabilities dynamically to evade static import inspection.

Evasion Technique

Direct Syscalls & EDR Hook Bypasses

Executing kernel transitions directly to blind security sensors

Endpoint Detection and Response (EDR) agents monitor application behavior by installing inline hooks (jump instructions) into user-mode system libraries such as ntdll.dll. When an application calls NtAllocateVirtualMemory, the hook redirects execution to the EDR sensor for inspection.

To bypass these user-mode sensors, advanced malware implements direct syscall stubs. Instead of calling through ntdll.dll, the malware loads the System Service Number (SSN) into register EAX and issues the CPU instruction syscall (opcode 0F 05) directly from its own code section.

Koltzi Detection Mechanism

Koltzi uses the Zydis disassembler to scan executable sections for unhooked syscall stubs. Legitimate user-mode applications never embed raw syscall instructions outside of ntdll.dll.

OS Internals

Process Environment Block (PEB) Traversal

Reading process metadata without Win32 API calls

The Process Environment Block (PEB) is a kernel-populated structure residing in user-mode memory containing process status, loaded DLL lists, environment variables, and debugger flags.

On 64-bit Windows, the Thread Environment Block (TEB) is accessed via the GS segment register. The PEB pointer is located at offset GS:[0x60] (or FS:[0x30] on 32-bit systems).

How Malware Exploits It

Malware reads PEB->Ldr->InMemoryOrderModuleList to locate the base addresses of kernel32.dll and ntdll.dll manually without calling GetModuleHandle. Koltzi distinguishes normal CRT stack cookie initializations from evasive multi-step module traversals.

Obfuscation

API Hashing (Dynamic Symbol Resolution)

Hiding sensitive function names from static string sweepers

Rather than storing plaintext API names like VirtualAllocEx or WriteProcessMemory in the binary, malware authors store 32-bit hash values calculated with algorithms like ROR13, DJB2, or CRC32.

At runtime, the binary traverses the Export Directory of system modules, hashes each exported function name, and compares the result against its stored hash value to retrieve the function pointer.

Koltzi Hash Sweeper

Koltzi scans assembly immediate values against a pre-indexed database of over 100,000 Win32 API hashes across ROR13, DJB2, and MurmurHash, recovering the original API names automatically.

Container Forensics

PE Overlay (Appended File Data)

Bytes appended beyond the declared boundaries of the PE format

A PE file specifies the exact raw file size of its last section in the Section Table. Any bytes appended to the file beyond this calculation constitute the overlay.

The Windows PE loader ignores overlay bytes when mapping the file into virtual memory. However, the executing binary can open its own disk file (via CreateFileW) and read the overlay bytes directly.

Common Uses

Legitimate installers (Nullsoft NSIS, Inno Setup) store installer archive archives in the overlay. Malware droppers use the overlay to store encrypted secondary payloads, configuration scripts, and keylogger stagers.

Threat Attribution

Imphash (Import Hash)

Standardized cryptographic fingerprint of dynamic import dependencies

Devised by Mandiant, Imphash creates an MD5 hash of an executable binary's imported libraries and function names formatted in a normalized, lower-case sequence.

Because compiler toolchains and threat frameworks generate consistent import sequences, different builds or packed variants created by the same author often share an identical imphash.

Forensic Value

Imphash allows security analysts to cluster related malware families and track adversary campaigns across different file hashes (MD5/SHA256).

Code Integrity

Authenticode Digital Signatures

Cryptographic certificate verification for binary author authenticity

Microsoft Authenticode uses Public Key Infrastructure (PKI) to embed digital signatures into PE files via the Security Directory (IMAGE_DIRECTORY_ENTRY_SECURITY).

A valid signature proves that the file originated from a trusted publisher and that the binary code has not been tampered with or modified since it was signed.

Triage Significance

Signed binaries from trusted software vendors provide a high confidence baseline for legitimate utility software. Conversely, unsigned executables performing administrative or injection operations warrant immediate containment.
